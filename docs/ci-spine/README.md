## Canonical naming without breaking existing gates

Proposed familiar display grammar: **`type(scope): purpose`**. Types: `ci`, `test`, `perf`, `build`, `docs`, and domain-specific names only after owner review. Scope identifies a canonical module or subsystem, not a temporary wave. Historical W/N IDs remain aliases and provenance. Also store independent dimensions: `suite`, `role`, `stage`, `trigger`, `repo`, `source_sha`, `workflow_blob_oid`, `job_id`, `run_id`, `run_attempt`, `event_time` and `knowledge_time`.

Examples: `test(taxonomy): title-parser-negatives`, `perf(gogreen): redtrace-history`, `ci(gogreen): required-admission`, `test(qps): excel-schedule-integration`, `test(jade): browser-contract`, `ci(federation): exact-head-receipts`. These are examples, not renamed live checks.

**Migration hazard:** `gogreen-required-gate-recheck.yml` listens to workflow completion events by old display name generated from ADMISSION. Workflows may also be linked by `workflow_run`, reusable caller references, dashboards and required job status contexts. Never batch-rename `name:` or `jobs.<id>` or change workflow filenames without an audited consumer migration. First approve aliases in an index; then select one OBSERVED noncritical pilot, simulate old/new reference resolution, regenerate the policy's name list with the canonical gate owner, test exact-head checks and rollback, and request independent review. Do not weaken any existing enforced gate.

## Dependency, venv, Node and browser cache tiers

Inspected 182 workflow files do not explicitly reference `actions/cache`, `setup-python` pip cache, `setup-node` dependency cache, or uv cache. This is YAML-level evidence, not proof that GitHub runners or existing tools never hit implicit caches.

- C0: pinned runtime/toolchain from runner or setup actions; key on OS, architecture, runtime ABI and tool version.
- C1: trusted, lockfile-keyed package download cache (pip/uv wheel, npm/yarn/pnpm store); cache restore may occur on less-trusted PRs but write scopes must be protected; never cache credentials.
- C2: immutable hashed wheelhouse/build artifact or OCI image with manifest and SBOM for heavier suites; exact digest readback.
- C3: job-local `.venv` installed from C1/C2; do **not** reuse a mutable 'global upper envelope' virtualenv across all projects: incompatible deps and accidental contamination can hide failures.
- C4: Playwright browser binaries cached only for matching Playwright version, OS and browser revision; runner OS dependencies validated separately.

**Controlled pilot:** same exact source SHA, platform, test population and lockfile. Compare A uncached baseline, B `setup-python` pip cache, C pinned `uv` with declared lock and cache, D browser image/cache, one cold and at least three warm runs, recording cache hit, resolver/download, build, tests, queue, wall time, p50/p95 and first-red. The measured 1-second Excel install has little savings headroom; the measured 28-second Playwright installation is a better candidate. Node action setup is available only where invoked; package caching, node problem matcher and registry auth are independent features, not blanket repo certifications.

External documentation: [setup-node](https://github.com/actions/setup-node), [setup-python](https://github.com/actions/setup-python), [uv CI](https://docs.astral.sh/uv/guides/integration/github/), [GitHub dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching). Cache design must not allow PR-controlled cache poisoning across protected refs.

## Fanout, async and temporal receipt design

- Native Actions `needs`, `workflow_call`, bounded `strategy.matrix.max-parallel` and purpose-specific `concurrency` groups cover most orchestration; all mandatory shards must finish or legitimately be NOT_APPLICABLE before fan-in.
- For Python I/O workers, use bounded `asyncio.TaskGroup` or an existing executor with semaphores/rate-limit backoff, retry classification and cancellation safety. GitHub hosted runners and Python asyncio are different schedulers.
- Serialize evidence as `repo/source_sha/workflow_blob_oid/job_id/run_id/run_attempt/observed_at/ingested_at/contract_digest`, with immutable artifact/sha256 and data-quality flags: SOURCE_BOUND, PARTIAL, STALE, DEFER, UNKNOWN, PASS, FAIL. Late/out-of-order events can append history but cannot replace newer authority.
- Integrate LDAB/DAB / Docker traces as read-only producers, not as an untrusted path to release authority; never run untrusted PR code from a privileged `workflow_run` handler. Reuse the existing actions metrics / scale-dock / golden-thread metric owners.

## Real setup-node capability assessment

The upstream GitHub action advertises four independent features. They are **features of an action**, not proof that this whole repository exercises them. The source scan found `actions/setup-node` in seven existing workflows (four MCEX factorial arms, M3 graph, N11 census, and P-process), pinned to a v4-era commit and Node 20/22. At this SHA none of those seven jobs configured `cache`, `cache-dependency-path`, `registry-url`, `scope`, or NODE_AUTH_TOKEN.

| setup-node feature | Actual Hub state | Qualification or next pilot |
| --- | --- | --- |
| Download/select Node and PATH | **Present in seven scoped jobs**; Node versions 20/22 | Prove each runner version and source-head binding; avoid interpreting as global coverage |
| Cache npm/yarn/pnpm download store | **Not explicitly configured** in inspected workflows | Pilot `cache: yarn` with `cache-dependency-path: app/yarn.lock`; never cache `node_modules` or secrets |
| Node/npm problem matchers | **Provided automatically wherever setup-node runs**, not a tested cross-repo guarantee | Verify diagnostic annotations on a deliberately failing safe fixture |
| npm/GitHub Package Registry authentication | **Not configured in the inspected setup-node callers** | Add only for an actual private-package/publishing consumer with least privilege and trusted OIDC/token policy |

Important: `app/yarn.lock` exists and `app/package.json` has `dev`, `build`, `start`, `lint` scripts but no `test` script. This is a JavaScript application-level test-population gap to investigate, not proof that JS tests elsewhere are absent. The package manifest also lists `react` 19.x and `react-dom` 18.x; investigate peer dependency compatibility in a bounded install, without presuming failure.

Upstream [setup-node README](https://github.com/actions/setup-node) says its package cache is the manager's global download store, **not `node_modules`**. Current versions may enable npm caching automatically when packageManager metadata identifies npm, while Yarn caching requires explicit `cache: yarn`. Do not enable cache on privileged workflows without a cache-poisoning threat assessment.
